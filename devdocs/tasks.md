# 架构优化
总体原则：
1. 从上往下层设计。
2. 把app包梳理，把所有要改动的文件重命名为原名.bak
3. 把要写的文件创建好（名字需讨论）
4. 每个文件只写字段、函数名字和签名和注释，函数内容就写几句注释，大致说他应该干什么，逻辑就直接写pass（字段、函数、签名需讨论）
5. 所有架构搭完后，可以参考对应的bak文件（可能名字要改，但是可以参考），把自己职责相关的内容填进去
6. 先不管下层内容，也不管还没写完代码的报错

## App 包架构梳理

当前只处理 `internal/app` 包，下层作为黑盒。设计记录见 [App 包设计](app-design.md)；骨架阶段暂不处理未实现代码导致的报错。

- [x] 自顶向下梳理 App 包，明确应用主体、职责层次和资源所有权。
- [x] 讨论并确认包内文件划分与文件名，在设计文档中记录职责、协作关系和确认状态。
- [x] 将确认需要改动的原文件重命名为 `原名.bak`，保留旧实现供后续参考；App 的 13 个生产文件和 12 个测试文件均已备份。
- [x] 按确认的文件划分创建 Go 骨架；逐项讨论字段、函数名和签名，写清职责注释，函数体以说明注释和 `pass` 占位。
- [ ] 全部架构与骨架确认后，再参考对应 `.bak` 文件，按新职责填入实现。

当前状态：App 六个文件的骨架已完成，启动耗时统计、业务线启停约定及资源所有权均已记录。函数体保留职责注释和 `pass`，实现、下层类型与进程入口适配尚未开展；旧测试保留在 `.bak` 中，随对应职责实现补充适用测试。
